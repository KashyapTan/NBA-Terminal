# Modular league fantasy UI integration

Exports from `nba_terminal/web/src/LeagueFantasy.tsx`:

- `useLeagueFantasy(api = leagueFantasyApi)`: mount once in App-owned shared composition. Exposes status, snapshot, loading, error, connect, selectTeam, disconnect, refresh. Request generations discard late status/snapshot responses after team changes or disconnect. Refresh failure retains old totals with their original fetched_at and an explicit error.
- `LeagueConnection({state})`: use on dashboard or another visible connection surface. Discovers teams after connection, selects verified/private or explicitly unverified/public team; documents actual local-only cookie POST flow. Password inputs clear immediately on submit. No cookies in React state, URLs, storage, error output, logs or fixtures.
- `LeagueDashboardSummary({state})`: optional dashboard summary including connection. Do not mount a duplicate LeagueConnection alongside this summary.
- `Matchups({snapshot, loading?, error?, onRefresh?})`: actual opponent first, all other league teams selectable, nine current matchup categories, attempt-weighted percentages, lower turnovers, ties, unknowns, today's reported rosters and timestamp. Selecting comparisons uses all same-period team totals already in the snapshot. Pass refresh as `() => void state.refresh()`.
- `WaiverWire({snapshot, onPlan?})`: filters explicitly eligible FREEAGENT rows against every roster; bounded market caveat, current/prior samples and averages, schedule/games/minutes gaps, editable ordered shortlist, explicitly selected droppable roster players, max four stream slots, verified weekly constraint inputs. Without onPlan it explicitly reports optimizer integration unavailable and never fabricates forecasts.

Mount into FantasyPage's dashboard/matchups/waiver ReactNode slots using shared hook state; no router or core FantasyPage/App edits are included here.

## Optimizer adapter seam

`onPlan(preferences: PlannerPreferences): Promise<WaiverPlan>` is deliberately a UI adapter seam, not a claimed production optimizer HTTP route. Integration worker owns the actual backend connection and output mapping. `WaiverPlan`/`PlanForecast` are UI view models, not raw optimizer dicts. Map the producer's forecast totals/games/minutes/probability fields into `totals`, `games`, `minutes`, `probability_five_wins`; category totals use pts/reb/ast/stl/blk/threes/to/fgm/fga/ftm/fta. Preserve nullable probabilities. Map actions into date/add_id/drop_id/stream_slot/gains/probability_gain and preserve assumptions, limitations, reasons, data_gaps. Per-action gains can include negative turnover/percentage tradeoffs; no browser optimization is done.

Preferences carry context `{league_id,team_id,matchup_period_id,fetched_at}`, user_confirmed_counts, user_confirmed_eligibility, weekly cap/used/available counts, candidate_ids ordered by preference, droppable_ids and max_stream_slots. Inputs and result reset on EVERY snapshot replacement, including refresh, team or matchup changes. Any edit invalidates the prior recommendation and in-flight results. Count edits clear confirmation. Candidate selection edits clear eligibility confirmation. The UI requires explicit verification of add/drop eligibility; unknown locks never become false silently. Selecting an unknown-lock player explicitly means the user verified that individual is unlocked. Reported locked=true players cannot be selected. Adapter must validate this scope, preserve user-confirmed provenance, override unknown data only for explicitly selected/confirmed facts, and otherwise return incomplete/unavailable with no actions.

If user counts are not confirmed, use server weekly counts only when cap is explicitly per scoring period AND all counts exist. Never use season acquisition counts. Validate all constraints again on backend. Counts used+available <= cap; unavailable adds may reflect extra restrictions, so equality is not required. Confirmed values are not attributed to ESPN.

Restrict add candidates to candidate_ids and initial droppable stream slots to droppable_ids; all other roster players remain locked for transactions while staying eligible for normal lineup forecasts. Preserve full team/opponent rosters and existing totals in forecasts. UI shortlist ordering is preference only; optimizer may choose different schedule/order. Unknown schedules, actual weekly usage, roster locks and uncertainty must remain gaps unless established or explicitly confirmed. Current/prior matchup history and uncertainty inference belong to backend adapter, never default constants in UI.
