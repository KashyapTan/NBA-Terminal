## Concrete findings and priority

### P0 — Preserve independently verified budget facts; don't invent defaults

`espn_fantasy.normalize:630–635` reads `settings.acquisitionSettings.matchupAcquisitionLimit` but sets cap only if `matchupLimitPerScoringPeriod is False` (except an absent-cap hardcoded7 fallback). `fantasy_planner_adapter:182` then rejects all API counts without that explicit False; `:196–205` also rejects a user-declared fallback unless False. The normalized usage can be valid6 while planner counts become all unknown. `cap_source=espn_acquisition_settings` can simultaneously accompany a null normalized cap, obscuring the rejection.

**SYNTHETIC reproduction:** provided cap7, omitted flag, explicit current-matchup map value6. Normalization retains `weekly_used_adds=6` but returns null cap/remaining; planner returns `unknown; daily acquisition rules are not modeled`, despite `matchup_add_limit_fallback=7`. See `reproductions.json.cap_flag_omission`. This establishes discarded facts, not that the user's payload has that exact omission.

**Is explicit per-day=false universally required?** No primary evidence found establishes that an absent ESPN flag means false. Upstream `BaseSettings` exposes it as `Optional[bool]` and preserves missing as None. Therefore a blanket `get(flag, False)` is unsupported. Equally, an omitted optional rule flag does not erase an explicit matchup ledger. Split `cap_value`, `cap_scope`, `cap_provenance`, `daily_rule_known` and `usage_period/value/source` instead of clearing all three counts. Accept the already-authorized user matchup cap7 as scoped user configuration; pair it with a fresh explicit current matchup counter if present. Preserve missing daily-rule knowledge separately. If policy requires daily-rule verification to call the entire plan transaction-feasible, keep that condition explicit rather than claiming cap or usage is absent. Explicit `true` means a daily limit needs a day ledger; never subtract total matchup acquisitions from a daily cap.

**LIVE counter evidence:** the historical basketball response has cap1 and daily flagtrue, while `transactionCounter.matchupAcquisitionTotals` has values up to10 in matchup22. The map is still matchup keyed under daily settings; it is not the current day's counter. Its keys2..22 differ from request/root scoringPeriod176 and currentMatchup22. `transactionCounter.acquisitions` is a separate season aggregate. This supports separating counter scope from enforcement scope.

**Correction contract:** request `mSettings+mTeam` fresh for the same league/season/team, record `status.currentMatchupPeriod=M`, parse nonnegative integral `teams[id=T].transactionCounter.matchupAcquisitionTotals[str(M)]`. Retain explicit0. Missing key/empty map remains unknown unless a verified schema contract or independently complete ledger establishes zero. Current implementation is appropriately conservative about absent keys. Do not reuse `acquisitions`, root `scoringPeriodId`, yesterday6, or a guessed week number. A missing counter can be repaired with one targeted mTeam refresh before asking for a current user input. Preserve cap7 without making the user repeat it.

If the matchup map still cannot be obtained, an explicit user confirmation of current used/remaining, bound to league/team/matchup and timestamp, is a transparent fallback. Daily `mTransactions2` rows alone are insufficient: only completed acquisition events across every matchup scoring day, all transaction pages, commissioner adjustments/count-exempt semantics and duplicates reconciled could produce a trustworthy alternative ledger. Do not default unknowns to0 or use trades/drops as adds. The global hardcoded `league_fallback_7` should become a context-bound user cap fallback; it is not a general ESPN league default.

### P0 — A partial NBA rate row can destroy complete ESPN rates

`fantasy_nba.fetch_rates:133–143` checks only PLAYER_ID, PLAYER_NAME, TEAM_ID, GP, MIN, PTS. `enrich_players:279+` selects any matched row with GP>0 and replaces the full rate mapping. Missing FGM/FGA/FTM/FTA/REB/etc then become None even if the ESPN current sample was complete. The adapter sees `season_rates` and disables prior repair before `_rates` rejects it.

**SYNTHETIC reproduction:** fresh row for LeBron with GP1/PTS20/MIN30 but omitted shooting columns overwrites complete ESPN FGM1 with None and labels sourceNBA. This is a definite recoverable source-selection defect, not observed provider schema drift in this session.

**Correction:** validate all primitive rate columns and finite nonnegative values plus makes<=attempts before selecting a source. Prefer a complete fresh NBA same-season sample; otherwise retain a complete ESPN same-season sample. If both partial, either select a complete older season basis explicitly or perform documented field/group fallback with FG and FT pairs always from the same sample, and retain per-field provenance. A dict existing is not evidence it is usable. Preserve raw rejected NBA row and rejection code in safe diagnostics. Same validation must apply to ESPN partial samples and stale NBA fallback.

### P0 — Historical ownership validation checks the wrong key

`fantasy_actuals.reconstruct:184` checks `playerPoolEntry.teamId` with default requestedteam. LIVE historical ESPN daily roster entries expose **onTeamId**, not teamId. A conflicting onTeamId therefore bypasses validation.

**SYNTHETIC reproduction:** daily active entry onTeamId999 under requestedteam1, empty known team schedule, is accepted as complete NBA reconstruction with no gaps. Fix to validate actual `onTeamId` when present against the **historical daily** side team ID; do not replace it with current roster ownership. Retain side-context policy for legitimately omitted ownership only when that policy is explicit. Duplicate/conflicting owners or player IDs must invalidate the affected day. This prevents false completeness rather than merely reducing warnings.

### P1 — 800 is an application budget, not an ESPN provider cap

`EspnClient.market:276–331` makes eight requests of100, then reports incomplete if no terminal page. `LeagueFantasy.tsx:1218` attributes this to ESPN: “ESPN returned a limited free-agent pool.” That is inaccurate when the application stopped voluntarily.

**LIVE historical pagination:** `kona_player_info`, FREEAGENT+WAIVERS, limit500, offset0/500/1000 returned **500/343/0**. Response root only `players`; **no totalPlayers**. The first two pages contain843 distinct IDs with no overlap. Thus a valid Fantasy basketball pool can exceed800, and missing `totalPlayers` is normal. This historical count is not the user's current market size. The present provider_total parser only checks a field that this provider response did not supply.

Retrieve relevant population using bounded batches, described below. Separate retrieval completeness from search candidate cap, and count each stage. A terminal page can establish that this filtered enumeration exhausted its observed result set at fetch time; it is not a guarantee that every active NBA player is represented by ESPN or that the plan is globally optimal.

### P1 — Scope warnings to selected forecast and preserve successful fallbacks

The normalizer emits missing-sample/schedule/counter messages across **all teams and market entries**, even if a selected roster/current sample is complete. Two other lines about game-start locks and transaction scope are emitted unconditionally (`espn_fantasy:715–720`): they are modeling notes, not evidence of failed fetches. Optional failed source messages should remain source diagnostics when an adequate fallback has already repaired the requested fact.

Do not silence an actually required selected-roster fact. Emit structured gaps with field, entity IDs, period, source, request failure/rejection, fallback attempted, selected basis and whether it blocks the current evaluation. The optimizer already distinguishes partial market coverage from required scoring/calendar/rate completeness. Keep that distinction. Lack of prior sample is not a gap if selected current rates are complete; absence of NBA-derived history is not missing banked scoring if complete official ESPN totals are selected.

## Efficient pool recovery plan

1. **Preserve broad enumeration capability.** Use500 (live verified) or250 player pages, max e.g.8 pages/4000 observed IDs with time/byte budget, limit+offset, dedupe ESPN IDs, stable supported ranking fields and repeated-page detection. A hard safety bound remains appropriate. Fetch one additional empty/short terminal page when needed. If server silently caps page size, detect it or use a conservative tested page size; a short page alone without stable terminal evidence can otherwise falsely imply exhaustion. Record request size and returnedsize separately.
2. **Don't call the active inventory a current NBA roster.** Public `F/players?view=players_wl` with header `{"filterActive":{"value":true}}` is LIVE1099 rows,251 proTeamId0; it includes historical players such as Ian Clark. It exposes identity/eligibleSlots/proTeamId/percentOwned, **not** league FREEAGENT status. Public “active” is ESPN universe eligibility, not proof of NBA contract/current minutes. It can support ID lookup and coverage diagnostics but cannot replace the league market.
3. **Build relevant season population once.** Prefer one CommonAllPlayers current-season roster/identity batch (includes players with no box-score sample) plus current LeagueDashPlayerStats and any league-rostered/pool candidates not matched, retaining unresolved new signings/rookies. Use season crosswalk rather than strict current-team rate matching. Filter out players proven irrelevant to remaining schedule only after retaining reason; do not silently discard all GP0 rookies as unavailable. If upstream roster batch unavailable, keep broad ESPN pool with explicit exclusion counts rather than asserting current-active completeness.
4. **Join league availability in bounded filterIds batches.** Use known IDs from league market; if introducing ESPN universe candidates, query league card/info batch and require observed current status and no conflicting onTeamId. Upstream proves filterIds for cards; exact combined status+ID filter behavior should be checked in an authorized request before relying on it. Don't assume an undocumented filterActive nested under players works on league pool: this research only verified the season endpoint's top-level filterActive.
5. **Batch cards only for relevant identities.** Current snapshot unions every roster and800 market IDs and throws league_too_large if>1000 before one card request. Raising market bound without fixing that dependency fails. Split requested card IDs into chunks100–250 (bounded concurrency2–4), preserve all roster cards, and enrich rates with one current/prior NBA batch; no per-player NBA loops. Keep optimizer candidate selection separate from inventory retrieval and the normalized1000-player limit.
